## 2. 优缺点对比

### 2.1 原始架构

| 维度           | 优点                                      | 缺点                           |
| -------------- | ----------------------------------------- | ------------------------------ |
| **开发体验**   | 纯 TypeScript，一套语言，无需 Rust 工具链 | 两端重复代码，bug 修复需改两处 |
| **构建依赖**   | 仅 Node.js + npm                          | 无跨语言类型检查               |
| **运行时性能** | JS 引擎原生执行，无跨语言边界             | GC 开销大，大对象处理慢        |
| **类型安全**   | TypeScript 编译时检查                     | 仅在 TS 层面，跨端数据无约束   |
| **一致性**     | 两端逻辑易产生分歧                        | 无法保证协议帧解析行为一致     |
| **包体积**     | 无额外二进制文件                          | JS 代码体积可被 tree-shake     |
| **全平台**     | Node.js 跨平台                            | 依赖 Node.js 环境              |

### 2.2 当前架构（WASM 共享）

| 维度           | 优点                                       | 缺点                            |
| -------------- | ------------------------------------------ | ------------------------------- |
| **开发体验**   | 单一真实源，修一处全生效                   | 需要 Rust + wasm-pack 工具链    |
| **构建依赖**   | Rust 编译产物为静态二进制                  | 首次构建需下载 wasm-bindgen CLI |
| **运行时性能** | WASM 接近原生速度，无 JS GC 压力           | 跨 JS 边界有序列化开销          |
| **类型安全**   | serde 强类型序列化，跨边界数据有保障       | WASM 导出类型需手动映射到 TS    |
| **一致性**     | 两端加载同一份二进制，不可能不一致         | 版本对齐需要构建脚本保证        |
| **包体积**     | ~460KB 单文件，无依赖链                    | 增加了 WASM 二进制文件          |
| **全平台**     | WebAssembly 标准，所有现代浏览器 + Node.js | 需要对应平台的 WASM 运行时      |

### 2.3 关键对比

| 对比项           | 原始架构                     | 当前架构                      |
| ---------------- | ---------------------------- | ----------------------------- |
| **协议帧解析**   | 两端各一份 TS 实现，易出分歧 | 同一 WASM 二进制，100% 一致   |
| **选择器生成**   | 仅扩展端有 TS 实现           | 双端共享，Server 也可用       |
| **流程引擎**     | 两端维护两份                 | 单一 WASM 状态机              |
| **MCP 缓存**     | 两端独立缓存逻辑             | 统一 TTL 策略                 |
| **Bug 修复成本** | ×2（两端各改）               | ×1（改 Rust 一处）            |
| **新增功能成本** | ×2（两端各实现）             | ×1（Rust 实现，两端自动可用） |

## 3. 全平台运行分析

### 3.1 WebAssembly 跨平台性

WASM 本身是**平台无关**的字节码格式。只要目标环境有 WASM 运行时（WebAssembly Virtual Machine），就可以执行。

| 平台                      | Chrome Extension | Native Server (Node.js) | 说明                    |
| ------------------------- | ---------------- | ----------------------- | ----------------------- |
| **macOS (x64)**           | ✅               | ✅                      | 已验证通过              |
| **macOS (Apple Silicon)** | ✅               | ✅                      | WASM 与 CPU 无关        |
| **Windows (x64)**         | ✅               | ✅                      | Node.js 内置 WASM 支持  |
| **Linux (x64)**           | ✅               | ✅                      | Chrome + Node.js 均支持 |
| **Linux (ARM64)**         | ✅               | ✅                      | WASM 不依赖 CPU 架构    |

### 3.2 各层级全平台支持

#### Chrome Extension 层

| 平台    | 支持 | 说明                     |
| ------- | ---- | ------------------------ |
| Windows | ✅   | Chrome/Edge 完整支持 MV3 |
| macOS   | ✅   | Chrome 完整支持 MV3      |
| Linux   | ✅   | Chrome 完整支持 MV3      |

WASM 在浏览器端运行，由 V8 引擎提供 WebAssembly 支持，**与操作系统无关**。

#### Native Server 层

| 平台    | 支持 | 说明                   |
| ------- | ---- | ---------------------- |
| Windows | ✅   | Node.js v20+ 内置 WASM |
| macOS   | ✅   | 已验证                 |
| Linux   | ✅   | Node.js v20+ 内置 WASM |

Node.js 从 v8.4 开始内置 WebAssembly 支持（通过 V8），v20+ 对 WASM 有完整支持。**不需要额外安装 wasm-pack 或 Rust 运行时**。

#### 限制因素

| 限制             | 说明                       | 影响范围      |
| ---------------- | -------------------------- | ------------- |
| **Node.js 版本** | 需要 v20+（WASM 支持完善） | Native Server |
| **Chrome 版本**  | 需要支持 Manifest V3       | Extension     |
| **WASM 运行时**  | 目标环境需支持 WebAssembly | 全平台都支持  |

**结论**：当前架构可以全平台运行，无平台绑定代码。

### 3.3 原生依赖对比

| 组件                 | 原始架构                   | 当前架构                              |
| -------------------- | -------------------------- | ------------------------------------- |
| **Chrome Extension** | 纯 JS，无原生依赖          | 增加 WASM（~460KB），浏览器内置运行时 |
| **Native Server**    | `better-sqlite3`（需编译） | 同上 + WASM（Node.js 内置运行时）     |
| **构建环境**         | 仅需 Node.js               | 需 Rust + wasm-pack（仅构建时）       |

**关键区别**：

- 原始架构：`better-sqlite3` 等平台特定的原生模块需要在每个目标平台上重新编译（node-gyp）
- 当前架构：WASM 是**跨平台的通用二进制**，一份编译产物可以在所有平台上运行，**不需要在目标平台上重新编译**

## 4. 总结

### 当前架构的绝对优势

1. **单一真实源** — 修 bug 只需改一处，不会有两端不一致的问题
2. **跨平台二进制** — 一份 WASM 产物全平台运行，不像 `better-sqlite3` 需要 per-platform 编译
3. **类型安全** — Rust 编译时即保证内存安全和类型正确
4. **性能** — 协议解析、选择器计算在 WASM 中完成，无 JS GC 开销

### 当前架构的代价

1. **工具链** — 需要 Rust + wasm-pack（仅开发者需要，用户无感知）
2. **语言切换** — 开发需要理解 Rust + TypeScript 两种语言
3. **构建时间** — WASM 编译需要额外时间（首次 ~30s，后续 <1s）
